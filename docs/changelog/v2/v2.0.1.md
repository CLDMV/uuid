# `@cldmv/uuid` v2.0.1 Changelog

**Release Date**: November 2026
**Release Type**: Patch
**Branch**: `release/2.0.1`

---

## Overview

v2.0.1 fixes how the library describes and generates UUIDs.

- `UUID.validate()` and `UUID.validateDetailed()` take a UUID string or a `UUID` instance; `validateDetailed()` threw a `TypeError` on a string.
- `getInfo()`, `validate()` and `validateDetailed()` describe every UUID, RFC or custom, with the same fields. They used to read the custom-variant bit positions on RFC ids too, which gave RFC ids made-up subvariants, versions and issuer categories.
- RFC version 1, 6 and 7 ids report the timestamp they hold, and `UUID.compare()` sorts them by time alongside TA and TB ids.
- `UUID.v1()` and `UUID.v6()` wrote the wrong timestamp into every id. They now match the RFC 9562 test vectors.

Generated TA, TB and IA ids and their timestamps are unchanged. Code that reads the validator report or `getInfo()` should check the upgrade notes: a few fields were renamed or now return `null`.

## 🐛 Bug Fixes

### `validate()` and `validateDetailed()` accept strings and instances ([#120](https://github.com/CLDMV/uuid/pull/120), fixes [#119](https://github.com/CLDMV/uuid/issues/119))

Both methods only took the 16 raw bytes. Given a string, `validate()` threw `UUID must be a 16-byte buffer`, and `validateDetailed()` handed the string to the hex encoder and threw `TypeError [ERR_INVALID_ARG_TYPE] … at toHex`. Both now take a UUID string (with or without dashes, either case), a `UUID` instance or 16 bytes. A string that isn't 32 hex digits throws `Invalid UUID string`.

### Every UUID gets the same detail fields (fixes [#123](https://github.com/CLDMV/uuid/issues/123))

The variant is bits 64-66: RFC 4122/9562 ids are `10x`, custom ids are `111`. The detail methods read bits 67-68 (subvariant), 75-78 (version) and 79-88 (issuer ID) on every id, but those fields only exist under `111`. An RFC v4 id came back with `version: 14`, `issuerID: 276` and `issuerCategory: "Category B (Open Source Contributors)"`.

One decoder now describes every id, and a field the id's variant doesn't define is `null`:

- `getInfo()` returns `uuid`, `isUUID`, `variant`, `variantFamily`, `subvariant`, `version`, `variantIdentifier`, `issuerID`, `issuerCategory`, `timestamp`, `timestampUnit`, `date`, `isIssuerVariant` and `isTimestampVariant` for every id. `version` is bits 75-78 on a custom id and the RFC version (bits 48-51) on an RFC id. `variantFamily`, `timestampUnit` and `date` are new.
- RFC v1 and v6 (100-ns intervals) and v7 (milliseconds) ids report their timestamp on the Unix epoch. `getTimestamp()` and `getTimestampBigInt()` cover them, the new `getTimestampUnit()` gives the unit, and `UUID.compare()` puts them in time order with TA and TB ids.
- The RFC Nil and Max ids are RFC ids. Max (all ones) used to read as a custom id with reserved subvariant `11`.
- `getIssuerID()` and `getIssuerCategory()` return `null` for every id that isn't an Issuer Variant.
- `validate()` `fields` are the `getInfo()` fields plus the raw timestamp bit fields, named after the spec: `timestampLayout`, `timestampSign`, `timestampSegmentA` (bits 1-63), `timestampContinuation` (bits 69-74) and `timestampMagnitude`. `validateDetailed()`'s `bitLayout` and `entropy` sections also have the same keys for every id.
- The entropy section counts the real random bits: 49 for TA/TB, 109 for IA, 122 for RFC v4, 74 for RFC v7, `null` where there is no random field. It used to report 109 for everything and count timestamp bits as entropy.
- Issuer categories have one name everywhere (`"Category A (Well-Recognized Tech Entities)"`). Issuer IDs 512-1023 get the future RFC range warning again; the check compared against constants that didn't exist. Issuer 404's report no longer says Category B.
- Valid RFC ids no longer get the warning `Not a valid UUID`.

### `UUID.v1()` and `UUID.v6()` write RFC 9562 timestamps (fixes [#124](https://github.com/CLDMV/uuid/issues/124))

`v1()` wrote `time_hi` from the wrong bits, `v6()` laid the time field out 4 bits off, and both computed the 60-bit count of 100-ns intervals as a JavaScript number past 2^53, which drops low bits. Every v1 and v6 id the library generated held the wrong time; a 2023 id decoded as the year 4896 in any RFC parser. Both now compute the time as a bigint and produce the RFC 9562 test vectors byte for byte.

## Upgrade notes

- Calls that passed bytes to `validate()` / `validateDetailed()` work as before; strings and instances now work too.
- **Validator fields renamed:** `timestampLower63` is `timestampSegmentA`, `actualTimestamp` is `timestamp`, `reservedBit69` and `categoryValidation` are gone (bit 69 is in `timestampContinuation`), and `issuerCategory` uses the long names.
- **`null` for fields an id doesn't have:** `getIssuerID()`, `getIssuerCategory()` and `getInfo()`'s `subvariant`, `issuerID` and `issuerCategory` on RFC ids; missing keys in the validator sections are now present as `null`.
- **RFC timestamps:** `getTimestamp()` returns a value for RFC v1, v6 and v7 ids where it returned `null`. Code that used a non-null timestamp to mean "TA or TB" should check `isTimestampVariant()` instead. `UUID.compare()` now sorts those RFC ids by time instead of after all timestamp ids.
- **v1 and v6 ids generated by earlier versions** hold the wrong time and can't be corrected from the id alone. Generate new ones if anything reads their time.
