# `@cldmv/uuid` v2.0.1 Changelog

**Release Date**: November 2026
**Release Type**: Patch
**Branch**: `release/2.0.1`

---

## Overview

v2.0.1 fixes `UUID.validateDetailed()`, which threw a `TypeError` when given a UUID string. `UUID.validate()` and `UUID.validateDetailed()` now take a UUID string, a `UUID` instance or the 16 bytes.

Nothing else changed. Generated ids, timestamps and every other method behave as in v2.0.0.

---

## 🐛 Bug Fixes

### `validate()` and `validateDetailed()` accept strings and instances ([#120](https://github.com/CLDMV/uuid/pull/120), fixes [#119](https://github.com/CLDMV/uuid/issues/119))

Both methods only took the 16 raw bytes. Given a string, `validate()` threw `UUID must be a 16-byte buffer`, and `validateDetailed()` handed the string to the hex encoder and threw `TypeError [ERR_INVALID_ARG_TYPE] … at toHex` before it reached any check. `new UUID(id).getInfo()` on the same id worked, which made the failure look specific to the id.

Both now accept:

- a UUID string, with or without dashes, in either case;
- a `UUID` instance;
- a `Uint8Array` (or `Buffer`) of 16 bytes, as before.

A string that isn't 32 hex digits throws `Invalid UUID string`. Any other input to `validateDetailed()` throws `UUID must be a 16-byte buffer`, the same error `validate()` already gave. The TypeScript signatures are widened to `Uint8Array | string | UUID`.

## 🧪 Tests

- `validate()` and `validateDetailed()` are checked on the id from #119, on `TA()`, `TB()` and `IA()` ids, and on timestamp and issuer ids of versions 1-6, each passed as a dashed string, an undashed uppercase string, bytes and an instance; plus an RFC v4 id and the malformed-input errors ([#120](https://github.com/CLDMV/uuid/pull/120)).
