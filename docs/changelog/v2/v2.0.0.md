# `@cldmv/uuid` v2.0.0 Changelog

**Release Date**: November 2026
**Release Type**: Major
**Branch**: `release/2.0.0`

---

## Overview

v2.0.0 makes the whole timestamp range of the Timestamp Variant usable. The format has always held a sign bit and a 69-bit magnitude, ±(2^69 - 1): about ±18.7 trillion years for `TA()` (seconds) and ±18.7 billion years for `TB()` (milliseconds). Until now the code went through `Number` and `Math.abs`, so it couldn't take a value above 2^53 exactly, wrapped silently past 2^69, and lost precision when decoding large values. Every value in the range now goes in, comes back out and sorts exactly.

`TA()` and `TB()` mint two new timestamp versions, 5 and 6, which lay the whole magnitude out most significant bit first, so byte order (string order, a database `uuid` column) follows time across the full range. Versions 3 and 4 kept the top 6 magnitude bits after the variant field and only sorted within ±(2^63 - 1). Ids already minted (versions 1-4) keep decoding exactly as before, `UUID.migrate()` rewrites them into 5/6, and the new `UUID.compare()` sorts any mix of versions by time.

It is a major release for two reasons: `getTimestamp()` returns a `bigint` past ±(2^53 - 1), which widens its TypeScript type, and new ids are versions 5/6, which don't sort together with stored version 3/4 ids by byte order until those are migrated. See the upgrade notes.

## 💥 Breaking Changes

### `TA()` / `TB()` mint versions 5 and 6 ([#117](https://github.com/CLDMV/uuid/pull/117), fixes [#100](https://github.com/CLDMV/uuid/issues/100))

- Version 5 (seconds) and version 6 (milliseconds) store magnitude bits 68..6 at bits 1-63 and bits 5..0 at bits 69-74. Byte order follows time from -(2^69 - 1) to 2^69 - 1.
- `uuid.version()` still reports `"TA"` / `"TB"`; `getVersion()` returns 5 / 6 instead of 3 / 4.
- Versions 1-4 still decode, and `UUID.timestamp(ts, version)` still mints any of them.
- Inside one layout, ids sort by time as before. Across layouts they don't: a version 3/4 id sorts after a version 5/6 id of the same time. Migrate stored ids, or sort with `UUID.compare()`.

### `getTimestamp()` returns `number | bigint | null` ([#117](https://github.com/CLDMV/uuid/pull/117))

- A `number` while the value is a safe integer (±(2^53 - 1), about ±285,000 years in milliseconds), the exact `bigint` past that, `null` for non-timestamp ids. Every timestamp a JavaScript `Date` can hold is still a `number`, so runtime behavior only changes for values that used to come back rounded.
- TypeScript code typed against `number | null` (or passing the result straight to `new Date()` or arithmetic) needs updating.
- `getInfo().timestamp` follows the same rule.

### `UUID.migrate()` targets versions 5 and 6 ([#117](https://github.com/CLDMV/uuid/pull/117))

- Versions 1 and 3 become 5, versions 2 and 4 become 6. The sign, the timestamp and the 49 entropy bits are copied, so a version 2 id and its version 4 migration end up at the same version 6 id.
- `isLegacyTimestampLayout()` is true for versions 1-4.

## ✨ Features

### Full-range timestamp inputs ([#117](https://github.com/CLDMV/uuid/pull/117))

- `TA()`, `TB()`, `UUID.timestamp()` and the version modules take a `number`, a `bigint`, a decimal integer string (the exact form that survives JSON) or a `Date`.
- A fractional number is floored toward -Infinity, so `UUID.TA(Date.now() / 1000)` stores the second it falls in, and -0.5 sorts before 0. A `Date` is milliseconds for `TB()` and floored seconds for `TA()`.
- Values the format can't hold throw instead of encoding a different time: a `RangeError` for a magnitude past 2^69 - 1, `NaN`, `Infinity`, a malformed string or an invalid `Date`, a `TypeError` for any other type. `null` and `undefined` still mean now.

### `uuid.getTimestampBigInt()` ([#117](https://github.com/CLDMV/uuid/pull/117))

- Always the exact `bigint`, or `null` for non-timestamp ids.

### `UUID.compare(a, b)` ([#117](https://github.com/CLDMV/uuid/pull/117))

- A comparator for `Array.prototype.sort` over UUID instances, strings or 16-byte buffers. Timestamp Variant ids (versions 1-6) come first, ordered by the time they hold, exactly across the whole range; seconds and milliseconds go on one scale. Equal times, and every other UUID (which sorts after all timestamp ids), fall back to byte order.
- Use it for a mix of versions, `TA()` next to `TB()`, or version 3/4 ids past ±(2^63 - 1).

## 🐛 Bug Fixes

All from [#117](https://github.com/CLDMV/uuid/pull/117), fixes [#100](https://github.com/CLDMV/uuid/issues/100):

- `TB(2 ** 69)` decoded as 0 and `TB(-(2 ** 69))` as -0. Both now throw a `RangeError`.
- `TB(10n)` threw `Cannot convert a BigInt value to a number`. Bigints are now accepted.
- `TB(NaN)` / `TB(Infinity)` threw a BigInt conversion error. They now throw a `RangeError` saying the timestamp must be finite.
- `TB(-0.5)` decoded as -0 and sorted before `TB(0)`. Negative fractions now floor.
- Decoding an id with a magnitude above 2^53 was lossy in every version. It is now exact.
- The validator warned "Reserved bit 69 is set to 1" on every pre-1970 id. Bit 69 is a magnitude bit in the Timestamp Variant, so the warning is gone; `fields.reservedBit69` is still reported.
- The internal timestamp-independent entropy helper (`src/lib/entropy-sources.mjs`, not exported) was limited to 64 bits; it takes the same inputs and range as `TA()` / `TB()`.
- The timestamp encoding was copied five times (the four version modules and `UUID`); it now lives in one shared helper, `src/lib/timestamp.mjs`, which the validator uses as well.

## Upgrade notes

- **TypeScript:** change `number | null` annotations on `getTimestamp()` to `number | bigint | null`, or call `getTimestampBigInt()` when you want one type. Where you need a `Date`, `new Date(Number(id.getTimestamp()))` works for any time a `Date` can hold.
- **Stored ids:** ids from 1.x keep decoding to the same time. If anything orders them by bytes (a primary key, an index, `ORDER BY id`), new version 5/6 ids won't interleave correctly with them. Either migrate every stored id with `UUID.migrate()` (deterministic and idempotent, so migrate primary and foreign keys alike), or sort with `UUID.compare()` until you do. `isLegacyTimestampLayout()` finds the rows that need it.
- **Version checks:** code that tests `getVersion() === 3` / `=== 4` for TA/TB ids should accept 5 / 6 too, or use `version()` (`"TA"` / `"TB"`) instead.
- **Inputs:** values that used to encode silently wrong (past ±2^69, `NaN`, `Infinity`) now throw. Fractional and pre-1970 inputs keep working.
- To keep minting the 1.x layout for now, use `UUID.timestamp(ts, 3)` / `UUID.timestamp(ts, 4)`.
