# `@cldmv/uuid` v1.4.0 Changelog

**Release Date**: November 2026
**Release Type**: Minor
**Branch**: `release/1.4.0`

---

## Overview

v1.4.0 makes the Timestamp Variant sort by byte order. Until now `UUID.TA()` and `UUID.TB()` wrote the timestamp magnitude's low 32 bits ahead of its upper 31, so two ids compared as bytes only followed time inside one 2^32 window and reversed at every boundary: every 49.7 days for `TB` (milliseconds), every 136 years for `TA` (seconds). Any store that orders rows or cursors by a `TB` id broke silently at each rollover.

The fix is non-breaking and goes through the version field. Timestamp versions 3 (seconds) and 4 (milliseconds) carry the ordered layout, `UUID.TA()` and `UUID.TB()` now mint them by default, and versions 1 and 2 decode exactly as before, so every stored id keeps its timestamp. `UUID.migrate()` rewrites a stored legacy id to the ordered layout deterministically, and `isLegacyTimestampLayout()` selects the rows that need it.

## ✨ Features

### Timestamp versions 3 and 4 sort by byte order ([#90](https://github.com/CLDMV/uuid/pull/90), fixes [#89](https://github.com/CLDMV/uuid/issues/89))

- Versions 3 (seconds) and 4 (milliseconds) lay the magnitude out most significant bit first: the upper 31 bits at bits 1-31 and the low 32 at bits 32-63. The sign bit, the entropy bits and bits 69-74 are unchanged, so the version field is the only thing that tells the layouts apart.
- `UUID.TA()` mints version 3 and `UUID.TB()` mints version 4. An explicit `UUID.timestamp(ts, 1)` or `UUID.timestamp(ts, 2)` still mints the legacy layout for anyone who needs it.
- Versions 1 and 2 decode as before: `getTimestamp()` on an id minted by 1.3.1 or earlier answers the same value it always did.
- `validators.mjs` read segment A as one contiguous value, which was wrong for the legacy layout; it now reads by version.

### `UUID.migrate()` and `isLegacyTimestampLayout()` ([#90](https://github.com/CLDMV/uuid/pull/90))

- `UUID.migrate(input)` rewrites a legacy timestamp id to version 3 or 4 with the same sign, the same timestamp and the same 49 entropy bits, so the result is deterministic. It is idempotent, and an id that is not a Timestamp Variant passes through unchanged.
- `uuid.isLegacyTimestampLayout()` is true for a version 1 or 2 timestamp id, which is the test to select stored rows for migration.
- Old and new ids interleave in byte order until every row is migrated, because versions 1 and 2 keep the legacy layout. Ordering by byte value is chronological only once every id involved is at version 3 or 4.

### Types

- The `.d.mts` declarations cover the new timestamp version modules, `UUID.migrate()` and `isLegacyTimestampLayout()`, and the consumer type test exercises them.

## Upgrade notes

- No breaking changes; drop-in for v1.3.2. New `TA` and `TB` ids are versions 3 and 4; existing ids keep decoding.
- If you order rows or cursors by a `TB` or `TA` id, migrate the stored ids once: select the rows where `new UUID(id).isLegacyTimestampLayout()` is true and write back `UUID.migrate(id).toString()` (or `.toBuffer()`). Until the rewrite is complete, old and new ids interleave in byte order.
